# 看板编排器 — 分解手册

> **核心工作者生命周期**（包括 `kanban_create` 扇出模式和"分解，不执行"规则）通过 `KANBAN_GUIDANCE` 系统提示词块自动注入到每个看板流程中。当你是一个整个工作就是路由的编排器配置文件时，此技能是更深入的手册。

## 配置文件是用户配置的 — 不是固定的名册

Hermes 的设置差异很大。有些用户运行一个做所有事情的单一配置文件；有些运行一个小型团队（`docker-worker`、`cron-worker`）；有些运行一个他们自己命名的精选专家团队。**没有默认的专家名册** — 编排器技能不知道这台机器上存在哪些配置文件。

在扇出之前，你必须将分解基于实际存在的配置文件。调度器会静默地无法生成未知的受分配者名称 — 它不会自动纠正，不会建议，也不会回退。因此，在一个只有 `docker-worker` 的设置中，分配给 `researcher` 的卡片将永远停留在 `ready` 状态。

**步骤 0：在规划前发现可用的配置文件。**

使用以下方法之一：

- `hermes profile list` — 打印此机器上配置的配置文件表格。如果你有终端工具，通过它运行；否则询问用户。
- `kanban_list(assignee="<some-name>")` — 对单个名称进行完整性检查。对于未知的受分配者返回空列表（而不是错误），因此这只确认你已经在考虑的名称。
- **直接询问用户。** "你设置了哪些配置文件？" 当目标需要不止一个专家时，这是一个很好的第一轮问题。

将结果缓存在你的工作记忆中，供后续对话使用。每轮都重新询问会浪费工具调用。

## 何时使用看板（相对于直接完成工作）

当以下任何一项为真时，创建看板任务：

1.  **需要多个专家。** 研究 + 分析 + 写作是三个配置文件。
2.  **工作应在崩溃或重启后继续存在。** 长时间运行、重复或重要的任务。
3.  **用户可能想要介入。** 任何步骤中的人机交互。
4.  **多个子任务可以并行运行。** 扇出以提高速度。
5.  **预期需要审查/迭代。** 审查者配置文件在起草者输出上循环。
6.  **审计跟踪很重要。** 看板行在 SQLite 中永久保存。

如果*以上都不适用* — 这是一个小型的一次性推理任务 — 请改用 `delegate_task` 或直接回答用户。

## 抗诱惑规则

你的工作描述是"路由，不执行"。强制执行此规则的规则：

-   **不要自己执行工作。** 你的受限工具集通常甚至不包括用于实现的终端/文件/代码/网络工具。如果你发现自己"只是快速修复这个" — 停下来，为正确的专家创建一个任务。
-   **对于任何具体任务，创建一个看板任务并分配它。** 每次都这样做。
-   **在创建卡片之前拆分多通道请求。** 用户提示可能包含几个独立的工作流。首先提取这些通道，然后为每个通道创建一张卡片，而不是将不相关的工作捆绑到单个实施者卡片中。
-   **并行运行独立的通道。** 如果两张卡片不需要彼此的输出，让它们保持未链接状态，以便调度器可以将它们扇出。仅链接真正的数据依赖关系。
-   **永远不要将依赖的工作创建为独立的就绪卡片。** 如果一张卡片必须等待另一张卡片，请在原始的 `kanban_create` 调用中传递 `parents=[...]`。不要先创建它然后再链接，也不要依赖正文中的"等待 T1"之类的描述。
-   **如果没有专家适合可用的配置文件，询问用户要创建哪个配置文件或使用哪个现有配置文件。** 不要发明配置文件名称；调度器将静默地丢弃未知的受分配者。
-   **分解、路由和总结 — 这就是全部工作。**

## 分解手册

### 步骤 1 — 理解目标

如果目标不明确，请提出澄清问题。询问成本低；生成错误的团队成本高。

### 步骤 2 — 草拟任务图

在创建任何内容之前，大声（在你的回复中向用户）草拟图表。将每个具体的工作流视为候选卡片：

1.  从请求中提取通道。
2.  将每个通道映射到你在步骤 0 中发现的配置文件之一。如果一个通道不适合任何现有配置文件，询问用户使用或创建哪个配置文件。
3.  决定每个通道是独立的还是受另一个通道制约的。
4.  将独立通道创建为没有父链接的并行卡片。
5.  创建综合/审查/集成卡片，并带有指向它们所依赖通道的父链接。一个具有未完成父任务的子卡片从 `todo` 开始；调度器只有在每个父任务都完成后才将其提升到 `ready`。

应该扇出的提示示例（使用占位符配置文件名称 — 替换为用户设置中实际存在的名称）：
- "构建一个应用" → 一张卡片分配给面向设计的产品/UI方向角色，一张或两张卡片分配给工程角色进行实现，如果用户有评审角色，则后续添加一张集成/评审卡片。
- "修复阻塞问题并检查模型变体" → 一张实现卡片用于修复阻塞问题，加上一张发现/研究卡片用于配置/源码验证。最终的评审卡片可以依赖于两者。
- "研究文档并实现" → 文档研究卡片可以与代码库发现卡片并行运行；实现仅在确实需要这些发现时才等待。
- "分析此截图并找到相关代码" → 一张卡片分配给具备视觉分析能力的角色进行视觉分析，同时另一张卡片搜索代码库。

像"也"、"最后"或"和"这样的词语并不自动意味着依赖关系。它们通常意味着"在回复之前确保这一点已被覆盖"。仅当一个卡片无法开始，直到另一个卡片的输出存在时，才链接任务。

在创建卡片之前向用户展示图表。让他们进行修正——包括每个泳道应该由哪个实际角色名称拥有。

### 步骤 3 — 创建任务并链接

使用步骤 0 中的角色名称。下面的示例使用了占位符 `<profile-A>`、`<profile-B>`、`<profile-C>`——用用户实际拥有的角色替换它们。

```python
t1 = kanban_create(
    title="研究：Postgres 成本与当前对比",
    assignee="<profile-A>",  # 在此设置中处理研究的角色
    body="比较 3 年窗口内的预估基础设施成本、迁移成本和持续运营成本。来源：AWS/GCP 定价、团队时间估算、同行的当前 Postgres 账单。",
    tenant=os.environ.get("HERMES_TENANT"),
)["task_id"]

t2 = kanban_create(
    title="研究：Postgres 性能与当前对比",
    assignee="<profile-A>",  # 同一角色，并行运行
    body="在我们预期的数据量（约 500GB，峰值 10k QPS）下比较查询延迟、吞吐量和扩展特性。来源：基准测试论文、公开案例研究、如果方便的话使用 pgbench 结果。",
)["task_id"]

t3 = kanban_create(
    title="综合迁移建议",
    assignee="<profile-B>",  # 负责综合/分析的角色
    body="阅读 T1（成本）和 T2（性能）的发现。生成一份 1 页的建议，明确权衡利弊并给出执行/不执行的结论。",
    parents=[t1, t2],
)["task_id"]

t4 = kanban_create(
    title="起草决策备忘录",
    assignee="<profile-C>",  # 起草面向用户文案的角色
    body="将分析师的建议转化为一份 2 页的备忘录，提交给 CTO。与团队知识库中先前决策备忘录的语调保持一致。",
    parents=[t3],
)["task_id"]
```

`parents=[...]` 控制晋升——子卡片保持在 `todo` 状态，直到每个父卡片都达到 `done` 状态，然后自动晋升到 `ready`。无需手动协调；调度器和依赖引擎会处理它。

如果任务图存在依赖关系，首先创建父卡片，捕获它们返回的 ID，并在创建子卡片的 `kanban_create` 调用中将这些 ID 包含在子卡片的 `parents` 列表中。避免并行创建所有卡片然后再链接它们；这会造成一个窗口期，调度器可能在子卡片的输入存在之前就认领它。

### 步骤 4 — 完成你自己的任务

如果你自己是作为一个任务生成的（例如，一个规划者角色被分配了 `T0: "调查 Postgres 迁移"`），请用你所创建内容的摘要来标记它为完成：

```python
kanban_complete(
    summary="分解为 T1-T4：2 个研究泳道并行，1 个综合任务基于它们的输出，1 个文案起草任务基于建议",
    metadata={
        "task_graph": {
            "T1": {"assignee": "<profile-A>", "parents": []},
            "T2": {"assignee": "<profile-A>", "parents": []},
            "T3": {"assignee": "<profile-B>", "parents": ["T1", "T2"]},
            "T4": {"assignee": "<profile-C>", "parents": ["T3"]},
        },
    },
)
```

### 步骤 5 — 向用户报告

用简单的语言告诉他们你创建了什么，并命名你使用的实际角色：

> 我已排队 4 个任务：
> - **T1** (`<profile-A>`): 成本比较
> - **T2** (`<profile-A>`): 性能比较，与 T1 并行
> - **T3** (`<profile-B>`): 综合 T1 + T2 形成建议
> - **T4** (`<profile-C>`): 将 T3 转化为 CTO 备忘录
>
> 调度器现在将认领 T1 和 T2。T3 在两者都完成后开始。当 T4 完成时，你会收到一个消息网关的 ping。使用仪表板或 `hermes kanban tail <id>` 来跟踪进度。

## 常见模式

**扇出 + 扇入（研究 → 综合）：** N 个无父卡片的研究风格卡片，一个综合卡片以它们所有为父卡片。

**并行实现 + 验证：** 一张实现者卡片进行更改，同时一张探索者/研究者卡片验证配置、文档或源码映射。一张评审卡片可以依赖于两者。不要仅仅因为用户在一个句子中同时提到了两者，就让实现者负责无关的验证。

**带门控的流水线：** `规划者 → 实现者 → 评审者`。每个阶段的 `parents=[previous_task]`。评审者阻塞或完成；如果评审者阻塞，操作员提供反馈并重新生成任务以解除阻塞。

**同角色队列：** N 个任务，全部分配给同一角色，它们之间没有依赖关系。调度器串行处理——该角色按优先级顺序处理它们，在其自身记忆中积累经验。

**人在回路：** 任何任务都可以 `kanban_block()` 以等待输入。在 `/unblock` 后调度器重新生成任务。评论线程承载完整的上下文。

## 陷阱

**发明不存在的角色名称。** 调度器会静默地无法生成未知的被分配者——卡片将永远停留在 `ready` 状态。始终分配给你在步骤 0 发现中的角色；如果不确定，请询问用户。

**将独立的泳道捆绑到一张卡片中。** 如果用户要求两个独立的结果，创建两张卡片。例如："修复阻塞问题并检查模型变体"不是一个修复者任务；为修复创建一个修复者/工程师卡片，为变体检查创建一个探索者/研究者卡片，然后可选地让评审依赖于两者。
**因措辞导致的过度链接。** 如果 X 是静态配置、文档或源码发现，那么“最后检查 X”可能仍与实现步骤并行。仅当检查依赖于实现结果时，才在实现之后链接它。

**忘记依赖链接。** 如果任务图显示 `research -> implement -> review`，不要将所有任务都创建为独立的就绪卡片。使用父级链接，这样实现/评审任务在其输入存在之前就无法运行。

**重新分配任务与创建新任务。** 如果评审者以“需要修改”为由阻止任务，请创建一个从评审者任务链接过来的**新**任务——不要带着严厉的表情重新运行同一个任务。这个新任务将分配给原始的实现者配置。

**链接的参数顺序。** `kanban_link(parent_id=..., child_id=...)` — 父级在前。混淆顺序会导致错误的任务被降级到 `todo` 状态。

**如果图的结构依赖于中间发现，不要预先创建整个图。** 如果 T3 的结构依赖于 T1 和 T2 的发现，就让 T3 作为一个“综合发现”任务存在，其自身的第一个步骤是读取父级交接并规划其余部分。编排器可以生成编排器。

**租户继承。** 如果您的环境中设置了 `HERMES_TENANT`，请在每次 `kanban_create` 调用时传递 `tenant=os.environ.get("HERMES_TENANT")`，以便子任务保持在同一个命名空间中。

## 恢复卡住的工作进程

当一个工作进程配置持续崩溃、产生幻觉或被其自身错误（通常是：错误的模型、缺少技能、凭证损坏）阻塞时，看板仪表盘会用 ⚠ 徽标标记该任务，并在抽屉中打开一个**恢复**部分。有三种主要操作：

1.  **回收**（或 `hermes kanban reclaim <task_id>`）— 立即中止正在运行的工作进程，并将任务重置为 `ready` 状态。现有的认领 TTL 约为 15 分钟；这是快速退出的路径。
2.  **重新分配**（或 `hermes kanban reassign <task_id> <new-profile> --reclaim`）— 将任务切换到另一个配置（存在于当前设置中的配置），并让调度器用一个全新的工作进程来拾取它。
3.  **更改配置模型** — 仪表盘会打印一个用于 `hermes -p <profile> model` 的复制粘贴提示，因为配置配置存储在磁盘上；在终端中编辑它，然后执行**回收**操作以使用新模型重试。

幻觉警告出现在以下任务上：工作进程的 `kanban_complete(created_cards=[...])` 认领包含了不存在的卡片 ID 或不是由该工作进程配置创建的卡片 ID（网关会阻止完成），或者自由格式的摘要引用了无法解析的 `t_<hex>` ID（建议性文本扫描，非阻塞）。两者都会产生审计事件，即使在恢复操作后也会保留——调试线索得以保留。
